## 1. Introduction and basic concepts

### What "middleware" is and why a robot needs it

A robot is not one program. It is many small programs running at once:
one reads the camera, one drives the wheels, one plans arm motions, one
decides what to do next. These programs need to talk to each other,
constantly, and they may even run on different computers (the camera
program on one board, the planner on a beefier machine). **Middleware**
is the plumbing that lets all those programs find each other and
exchange data in a common language, without each one hard-coding the
network address of every other.

If you have built web systems, think of middleware as the message bus /
service mesh of the robot: the part nobody "sees," that just makes sure
a message sent by one component reliably reaches the components that
care about it. By itself it does no vision, no driving, no planning —
its whole job is communication.

### What ROS 2 actually is (and is not)

**ROS 2** stands for "Robot Operating System 2," but the name is
misleading: **it is not an operating system.** It runs *on top of* a
normal OS (almost always Ubuntu Linux). ROS 2 is two things bundled
together:

- **A set of libraries** you call from your own code — in Python the
  library is `rclpy`, in C++ it is `rclcpp` — to send and receive
  messages, expose services, run long jobs, read parameters, and track
  geometry.
- **A set of command-line tools** (the `ros2` command) and graphical
  tools (`rviz2`, etc.) to inspect, debug, and launch a running robot.

So "writing a ROS 2 node" means "writing an ordinary Python or C++
program that imports the ROS 2 client library."

### The computation graph

When a ROS 2 system is running, the live set of programs and the
connections between them is called the **computation graph**:

- **Node** — one running program (one unit of work). The camera driver
  is a node; the navigation system is a node (really several). Nodes
  have names like `/camera_driver` and `/supervisor`.
- **DDS transport** — underneath, ROS 2 does not invent its own
  networking. It uses an industry standard called **DDS** (Data
  Distribution Service). DDS handles **discovery** (nodes finding each
  other automatically on the network, no central broker) and the actual
  byte-pushing. You rarely touch DDS directly; you just benefit from it.
  This is the big upgrade over ROS 1, and it is what gives ROS 2 its
  configurable reliability settings (see QoS, below).

A few more foundational words:

- **Distro (distribution)** — a named, versioned release of ROS 2,
  pinned to an Ubuntu version. This project targets **Jazzy Jalisco**
  (on Ubuntu 24.04) or **Humble Hawksbill** (on Ubuntu 22.04, supported
  as an LTS to 2027). A distro is like a Node.js LTS line: you pick one
  and everything in your project uses it.
- **Workspace** — a folder on disk where you keep and build your own
  ROS 2 code. By convention it has a `src/` directory.
- **Package** — the unit of code organization inside a workspace, like
  an npm package or a Python distribution. One package holds related
  nodes, message definitions, and launch files, plus a `package.xml`
  (metadata + dependencies) and, for Python, a `setup.py`.
- **`colcon`** — the build tool that compiles/installs every package in
  your workspace. You run `colcon build` once after writing code, then
  `source install/setup.bash` so the `ros2` tools can find your nodes.
- **`ros2` CLI** — the Swiss-army command for inspecting a running
  graph: list nodes, watch topics, call services, send action goals.

A minimal first-time flow looks like this:

```bash
# Source the distro so the ros2 command and libraries are on your PATH.
source /opt/ros/jazzy/setup.bash

# Build your own workspace's packages.
cd ~/shelf_ws
colcon build

# Overlay your freshly built packages on top of the distro.
source install/setup.bash

# Run a node from a package: ros2 run <package> <executable>
ros2 run demo_nodes_py talker
```

That is the whole mental model: **nodes** talk over a **graph** carried
by **DDS**, you organize code into **packages** inside a **workspace**,
build with **colcon**, and inspect with **ros2**.

## 2. Important concepts that are used most often

These are the building blocks you will use every day.

### Nodes

A **node** is one program in the graph. In `rclpy` a node is usually a
Python class that inherits from `rclpy.node.Node`. One node can publish,
subscribe, host services, run actions, and hold parameters all at once.

### Topics (publish / subscribe)

A **topic** is a named, one-way stream of messages. Any node can
**publish** (send) to a topic; any number of nodes can **subscribe**
(listen). Publishers and subscribers do not know about each other — they
only agree on the topic name and the message type.

> Web-dev framing: a topic is publish/subscribe, like an event bus or a
> WebSocket channel. You emit to a named channel; whoever subscribed
> gets it. Senders never directly reference receivers.

Every message has a **type** — a fixed data shape defined in advance,
like a typed struct. A simple built-in type is `std_msgs/String` (just a
string field). Real robot data uses richer types:
`sensor_msgs/Image` (a camera frame), `sensor_msgs/PointCloud2` (a 3-D
point cloud), `geometry_msgs/Twist` (a velocity command). In this
project the camera publishes images on
`/wrist_camera/color/image_raw`, a depth point cloud on
`/wrist_camera/depth/points`, the lidar publishes on `/scan`, the base
reports its motion on `/odom`, you command base velocity on `/cmd_vel`,
and the arm reports joint angles on `/joint_states`.

Use a **topic** when data flows continuously and the sender does not
need a reply: sensor streams, state reports, velocity commands.

### Services (request / response)

A **service** is a one-shot call-and-reply, like a function call across
the network. One node hosts the service; another calls it with a
**request** and waits for a single **response**.

> Web-dev framing: a service is a synchronous request/response, like a
> blocking RPC or a quick HTTP GET that returns once and is done.

Use a **service** for a fast question with a definite answer
("reset the odometry," "is the gripper open?"). Do **not** use a service
for anything slow — it blocks, and you get no progress along the way.

### Actions (long-running goals with feedback)

An **action** is for jobs that take real time and that you want to
monitor or cancel. You send a **goal**, then receive a stream of
**feedback** while it runs, then a final **result** when it finishes.

> Web-dev framing: an action is like a long-running async HTTP request
> that streams progress events and can be cancelled — a job you kick off
> and watch, not a call you block on.

Use an **action** for "drive to the shelf," "pick the product," "place
the product" — anything that takes seconds, reports progress, and might
need to be aborted. The whole place-on-shelf task is built from actions:
`navigate_to_shelf`, `pick_product`, `locate_slot`, `place_product`,
`verify_placement`.

Rule of thumb:

| You need… | Use |
|-----------|-----|
| A continuous stream, no reply | **Topic** |
| A quick question with one answer | **Service** |
| A slow job with progress + cancel | **Action** |

### Parameters

**Parameters** are named configuration values a node holds, set at
launch or at runtime — like environment variables or a config object.
For example a node might have a `picking_distance` parameter (how far in
front of the shelf to stop) or `planogram_path` (where the slot file
is). You read them with `get_parameter` and can change them live.

### QoS (Quality of Service) in one paragraph

Because the transport is DDS, each topic connection has tunable
**Quality of Service** settings that control reliability. The two you
will meet most: **reliability** (RELIABLE re-sends lost messages, like
TCP; BEST_EFFORT does not, like UDP), and **durability** (TRANSIENT_LOCAL
lets a late subscriber still get the last message a publisher sent,
useful for "set once" data like a map). A publisher and subscriber must
have *compatible* QoS or they silently won't connect — a classic
beginner trap. High-rate sensor streams often use BEST_EFFORT; commands
and one-shot state use RELIABLE.

### tf2 — the robot's shared sense of geometry

A robot has many **frames** — a frame is a labeled coordinate system
attached to a part of the robot or world (the floor, the base, the
camera, the gripper tip). The position-and-orientation of one thing
inside a frame is called a **pose**. The hard part is that the camera
sees a can "12 cm in front of the lens," but the arm needs to know where
that is in *its* coordinates.

**tf2** is the ROS 2 library that continuously tracks how every frame
relates to every other, as a tree, and converts a pose from one frame to
another for you. This project's frame tree is:

```
map → odom → base_link → arm_base_link → … → wrist_camera_link
                                          └→ tool0   (gripper tip)
```

- `map` — the fixed world / store floor.
- `odom` — a smooth, drift-prone estimate of where the base started.
- `base_link` — the mobile base itself.
- `arm_base_link` — where the arm is bolted to the base.
- `wrist_camera_link` — the camera's lens frame.
- `tool0` — the gripper's tip (the point that actually touches a can).

Ask tf2 "what is this point, expressed in `base_link`?" and it walks the
tree and does the math. Every other layer relies on this.

### Launch files

Starting twenty nodes by hand is painful. A **launch file** (a Python
or XML file) starts many nodes at once with their parameters set — like
a `docker-compose.yml` for ROS nodes. You run it with `ros2 launch`.

### Common CLI

```bash
ros2 run <pkg> <exe>          # start one node
ros2 node list                # list running nodes
ros2 topic list               # list active topics
ros2 topic echo /odom         # print messages flowing on a topic
ros2 topic hz /scan           # measure a topic's publish rate
ros2 service list             # list services
ros2 service call <srv> <type> "{...}"   # call a service once
ros2 action list              # list actions
ros2 action send_goal <act> <type> "{...}"  # send an action goal
ros2 param list /supervisor   # list a node's parameters
ros2 param get  /supervisor planogram_path
```

Two more tools, one line each:

- **rviz2** — a 3-D visualizer to *see* the robot, its frames, the
  point cloud, and planned paths while it runs.
- **rosbag2** — a recorder that captures topics to a file so you can
  replay a run later (great for debugging without the real robot).

## 3. Hello world example with code

The canonical first ROS 2 program is **talker / listener**: one node
publishes strings on a topic, another subscribes and prints them. We
will put both in a package called `shelf_demo`.

### The publisher (talker)

```python
# shelf_demo/talker.py
import rclpy                       # the ROS 2 Python entry point
from rclpy.node import Node        # base class for every node
from std_msgs.msg import String    # the message type we publish


class Talker(Node):
    def __init__(self):
        # Give the node a unique name in the graph.
        super().__init__("talker")

        # Create a publisher: (message type, topic name, queue depth=10).
        # Queue depth is how many outgoing messages to buffer.
        self.pub = self.create_publisher(String, "chatter", 10)

        self.count = 0
        # Call self.tick() every 0.5 seconds (a ROS timer, not sleep()).
        self.timer = self.create_timer(0.5, self.tick)

    def tick(self):
        msg = String()                          # make an empty message
        msg.data = f"hello shelf {self.count}"  # fill its one field
        self.pub.publish(msg)                   # send it on "chatter"
        self.get_logger().info(f"published: {msg.data}")  # ROS logging
        self.count += 1


def main():
    rclpy.init()              # start up the ROS 2 client library
    node = Talker()
    rclpy.spin(node)          # hand control to ROS: process timers/callbacks
    node.destroy_node()       # clean up on shutdown (Ctrl-C)
    rclpy.shutdown()


if __name__ == "__main__":
    main()
```

`rclpy.spin(node)` is the event loop: it blocks and keeps calling your
timers and callbacks until you stop the program. This is the same shape
as an async runtime's "run forever."

### The subscriber (listener)

```python
# shelf_demo/listener.py
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class Listener(Node):
    def __init__(self):
        super().__init__("listener")
        # Subscribe: (type, topic, callback, queue depth).
        # on_msg runs every time a message arrives on "chatter".
        self.sub = self.create_subscription(
            String, "chatter", self.on_msg, 10)

    def on_msg(self, msg):
        self.get_logger().info(f"heard: {msg.data}")


def main():
    rclpy.init()
    node = Listener()
    rclpy.spin(node)          # blocks, firing on_msg as messages come in
    node.destroy_node()
    rclpy.shutdown()


if __name__ == "__main__":
    main()
```

### Package essentials: `package.xml` and `setup.py`

A Python package needs two metadata files so `colcon` can build it and
`ros2 run` can find the executables.

`package.xml` declares the package and its dependencies:

```xml
<?xml version="1.0"?>
<package format="3">
  <name>shelf_demo</name>
  <version>0.0.1</version>
  <description>Talker/listener demo for the shelf project.</description>
  <maintainer email="you@example.com">you</maintainer>
  <license>Apache-2.0</license>

  <!-- ament_python is the build system for Python packages. -->
  <buildtool_depend>ament_python</buildtool_depend>

  <!-- Runtime dependencies: the ROS 2 Python lib and the message pkg. -->
  <exec_depend>rclpy</exec_depend>
  <exec_depend>std_msgs</exec_depend>

  <export>
    <build_type>ament_python</build_type>
  </export>
</package>
```

`setup.py` registers the two scripts as runnable executables. The
`entry_points` block is the important part — `name = module:function`
maps the name you type after `ros2 run` to the `main()` to call:

```python
from setuptools import setup

package_name = "shelf_demo"

setup(
    name=package_name,
    version="0.0.1",
    packages=[package_name],
    install_requires=["setuptools"],
    zip_safe=True,
    maintainer="you",
    license="Apache-2.0",
    entry_points={
        "console_scripts": [
            "talker = shelf_demo.talker:main",
            "listener = shelf_demo.listener:main",
        ],
    },
)
```

### Running it

```bash
cd ~/shelf_ws
colcon build --packages-select shelf_demo
source install/setup.bash

# In one terminal:
ros2 run shelf_demo talker
# In a second terminal (remember to source install/setup.bash there too):
ros2 run shelf_demo listener
```

The listener prints `heard: hello shelf 0`, `heard: hello shelf 1`, …
You can also spy on the stream without writing any code:

```bash
ros2 topic echo /chatter
```

That round trip — publish, subscribe, inspect from the CLI — is the
core skill everything else builds on.

### One short C++ note

The same talker in C++ uses `rclcpp` instead of `rclpy`; the shapes are
identical (a `Node` subclass, `create_publisher`, a timer):

```cpp
// Equivalent publisher in C++ (rclcpp). Same concepts, different syntax.
auto node = std::make_shared<rclcpp::Node>("talker");
auto pub  = node->create_publisher<std_msgs::msg::String>("chatter", 10);
// ...publish std_msgs::msg::String messages on a timer, then rclcpp::spin(node).
```

For this project we write our own nodes in **Python (`rclpy`)** because
it is faster to iterate; C++ matters mainly inside high-performance
layers we *consume* rather than write (MoveIt 2, parts of Nav2).

## 4. A bit advanced example with code

Now the two ingredients the pick-and-place loop truly depends on:
**actions** and **tf2**.

### Why pick-and-place needs actions and tf2

- **Actions:** picking a can or driving to a shelf takes seconds, can
  fail, and you want progress. A blocking service call would freeze the
  supervisor and give no way to cancel or report status. Actions give a
  goal → feedback stream → result, with cancellation — exactly the shape
  of every step in the loop.
- **tf2:** the camera reports the can's pose in its own
  `wrist_camera_link` frame, but the arm plans in `base_link`. Without
  tf2 converting between frames, "the can is here" is meaningless to the
  arm. Every grasp depends on this conversion being correct.

### A custom action shape

Other layers expose actions; let's define a realistic one for picking.
Action definitions live in a `.action` file (three sections separated by
`---`: goal, result, feedback):

```
# PickProduct.action

# --- GOAL: what we ask for ---
string sku                 # which product, e.g. "soup_can_400g"
geometry_msgs/PoseStamped grasp_pose   # where to grasp it (a pose + frame)
---
# --- RESULT: what we get back when done ---
bool success
string message
---
# --- FEEDBACK: streamed while it runs ---
string stage               # e.g. "approaching", "closing_gripper"
float32 progress           # 0.0 .. 1.0
```

### A Python action client

This client sends a `pick_product` goal and prints feedback as it
streams in. (The matching *server* lives in the grasping/arm layer; here
we are the caller.)

```python
# shelf_demo/pick_client.py
import rclpy
from rclpy.action import ActionClient        # the action client helper
from rclpy.node import Node
from geometry_msgs.msg import PoseStamped
from shelf_msgs.action import PickProduct     # our custom action type


class PickClient(Node):
    def __init__(self):
        super().__init__("pick_client")
        # (node, action type, action name) — name must match the server.
        self._client = ActionClient(self, PickProduct, "pick_product")

    def send(self):
        # Wait until the action server is actually up before sending.
        self._client.wait_for_server()

        goal = PickProduct.Goal()
        goal.sku = "soup_can_400g"

        # Build the grasp pose. PoseStamped = a pose plus the frame it is
        # measured in. We say "in base_link" so the arm understands it.
        gp = PoseStamped()
        gp.header.frame_id = "base_link"
        gp.pose.position.x = 0.45      # 45 cm in front of the base
        gp.pose.position.z = 0.30      # 30 cm up
        gp.pose.orientation.w = 1.0    # no rotation (valid quaternion)
        goal.grasp_pose = gp

        # send_goal_async returns a future. We attach a callback that
        # fires once the server accepts (or rejects) the goal, and pass
        # a feedback_callback that fires on every feedback message.
        future = self._client.send_goal_async(
            goal, feedback_callback=self.on_feedback)
        future.add_done_callback(self.on_goal_response)

    def on_feedback(self, fb):
        # fb.feedback is the Feedback part of the action.
        f = fb.feedback
        self.get_logger().info(f"  {f.stage} ({f.progress:.0%})")

    def on_goal_response(self, future):
        handle = future.result()
        if not handle.accepted:
            self.get_logger().error("goal rejected")
            return
        # Ask for the final result; another future, another callback.
        handle.get_result_async().add_done_callback(self.on_result)

    def on_result(self, future):
        result = future.result().result
        self.get_logger().info(
            f"done: success={result.success} ({result.message})")
        rclpy.shutdown()      # stop once the pick is finished


def main():
    rclpy.init()
    node = PickClient()
    node.send()
    rclpy.spin(node)          # keep processing the feedback/result futures


if __name__ == "__main__":
    main()
```

The chain of `*_async` calls and `add_done_callback` is ROS 2's way of
not blocking the node while a multi-second job runs — the same idea as
chaining promises so the event loop stays responsive.

### A tf2 lookup example

Here we convert a point the camera saw (in `wrist_camera_link`) into the
arm's `base_link` frame.

```python
# shelf_demo/tf_lookup.py
import rclpy
from rclpy.node import Node
from tf2_ros import Buffer, TransformListener   # the tf2 client side
from geometry_msgs.msg import PointStamped
from tf2_geometry_msgs import do_transform_point  # transforms a point


class TfLookup(Node):
    def __init__(self):
        super().__init__("tf_lookup")
        # The Buffer stores the recent frame tree; the Listener fills it
        # by subscribing to the /tf topics in the background.
        self.buffer = Buffer()
        self.listener = TransformListener(self.buffer, self)
        self.timer = self.create_timer(1.0, self.tick)

    def tick(self):
        # A point the camera reports: 12 cm straight out of the lens.
        p = PointStamped()
        p.header.frame_id = "wrist_camera_link"
        p.point.x = 0.0
        p.point.y = 0.0
        p.point.z = 0.12

        try:
            # Ask tf2 for the transform from the camera frame to base_link.
            # rclpy.time.Time() means "the latest available transform".
            tf = self.buffer.lookup_transform(
                "base_link", "wrist_camera_link", rclpy.time.Time())
        except Exception as e:
            # Early on the tree may not be populated yet; just wait.
            self.get_logger().warn(f"tf not ready: {e}")
            return

        # Apply the transform: same physical point, base_link coordinates.
        p_base = do_transform_point(p, tf)
        self.get_logger().info(
            f"point in base_link: "
            f"({p_base.point.x:.3f}, {p_base.point.y:.3f}, "
            f"{p_base.point.z:.3f})")


def main():
    rclpy.init()
    rclpy.spin(TfLookup())


if __name__ == "__main__":
    main()
```

Note the argument order of `lookup_transform(target, source, time)`:
"give me the transform that takes a point **from** `wrist_camera_link`
**into** `base_link`." Getting this order backwards is the most common
tf2 mistake — the can ends up mirrored to the wrong side of the robot.

## 5. Explanation of place-on-shelf code

Now we assemble the project's glue. The orchestration layer
([`../07-orchestration.md`](../07-orchestration.md)) will eventually be a
Behavior Tree, but to learn the mechanics we write a plain Python
**supervisor** node: a stand-in that calls the project's five actions in
order. The actions themselves are provided by the other layers —
navigation, grasping/arm, perception — so the supervisor only
*sequences* them.

The five actions, in order, are:

1. `navigate_to_shelf` — drive to the picking pose (Nav2 layer).
2. `pick_product` — grasp one can from the tray (arm + grasping layers).
3. `locate_slot` — find the next empty slot on the shelf (perception).
4. `place_product` — set the can down upright in the slot (arm layer).
5. `verify_placement` — confirm it's there and upright (perception).

### A perception-style publisher (the camera stand-in)

First, a tiny example of the kind of node the perception layer runs: it
takes the camera point cloud and publishes the shelf's detected pose.
For learning we publish a fixed pose; the real node would compute it.

```python
# shelf_demo/shelf_pose_pub.py
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import PoseStamped


class ShelfPosePub(Node):
    def __init__(self):
        super().__init__("shelf_pose_pub")
        # Publish where we think the shelf face is, in the map frame.
        self.pub = self.create_publisher(PoseStamped, "/shelf_pose", 10)
        # In reality this would subscribe to /wrist_camera/depth/points
        # and fit a plane to the shelf face; here we just emit a constant.
        self.timer = self.create_timer(1.0, self.tick)

    def tick(self):
        pose = PoseStamped()
        pose.header.frame_id = "map"          # measured in the world frame
        pose.header.stamp = self.get_clock().now().to_msg()  # timestamp it
        pose.pose.position.x = 3.0            # shelf is 3 m down the aisle
        pose.pose.position.y = 1.2
        pose.pose.orientation.w = 1.0         # facing the aisle
        self.pub.publish(pose)


def main():
    rclpy.init()
    rclpy.spin(ShelfPosePub())
```

Line by line: we create a publisher for `PoseStamped` on `/shelf_pose`;
a `PoseStamped` is a pose **plus** the frame and timestamp it belongs to
(without the `frame_id` the number "3.0" would be meaningless). We stamp
it with the current ROS clock so downstream nodes and tf2 can line it up
in time. Every second we publish the shelf's pose in `map`. A real
perception node has the same skeleton — only `tick` changes, replacing
the constants with a plane fit of `/wrist_camera/depth/points`.

### The supervisor node

This node calls the five actions in sequence. Each action runs to
completion before the next begins; if any fails, the supervisor logs it
and safe-stops (per requirements §7).

```python
# shelf_demo/supervisor.py
import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient

# Each layer ships its own action type; we import all five.
from shelf_msgs.action import (
    NavigateToShelf, PickProduct, LocateSlot,
    PlaceProduct, VerifyPlacement,
)


class Supervisor(Node):
    def __init__(self):
        super().__init__("supervisor")

        # Read configuration as parameters (set in the launch file):
        # which SKU to stock, and where the planogram file lives.
        self.declare_parameter("sku", "soup_can_400g")
        self.declare_parameter("planogram_path", "/cfg/aisle_7.planogram")
        self.sku = self.get_parameter("sku").value

        # One action client per layer. The name string must match the
        # name the server advertised, or wait_for_server() hangs.
        self.nav    = ActionClient(self, NavigateToShelf,  "navigate_to_shelf")
        self.pick   = ActionClient(self, PickProduct,      "pick_product")
        self.locate = ActionClient(self, LocateSlot,       "locate_slot")
        self.place  = ActionClient(self, PlaceProduct,     "place_product")
        self.verify = ActionClient(self, VerifyPlacement,  "verify_placement")

    def call(self, client, goal, label):
        """Send one goal and block until it finishes. Returns the result,
        or None on failure. (Blocking here is fine: the supervisor has
        nothing to do but wait for the current step.)"""
        client.wait_for_server()                       # ensure layer is up
        send_future = client.send_goal_async(goal)
        rclpy.spin_until_future_complete(self, send_future)  # wait for accept
        handle = send_future.result()
        if not handle.accepted:
            self.get_logger().error(f"{label}: goal rejected")
            return None

        result_future = handle.get_result_async()
        rclpy.spin_until_future_complete(self, result_future)  # wait for done
        result = result_future.result().result
        self.get_logger().info(f"{label}: success={result.success}")
        return result if result.success else None

    def run_once(self):
        """Place a single product: the §6 loop, steps 2 through 7."""

        # Step 2 — drive to the shelf and stop at the picking pose.
        nav_goal = NavigateToShelf.Goal()
        nav_goal.shelf_id = "aisle_7_bay_3"
        if self.call(self.nav, nav_goal, "navigate_to_shelf") is None:
            return self.safe_stop("navigation failed")

        # Step 4 — pick one product from the (known) tray layout.
        pick_goal = PickProduct.Goal()
        pick_goal.sku = self.sku
        if self.call(self.pick, pick_goal, "pick_product") is None:
            return self.safe_stop("pick failed")

        # Step 5 — find the next empty slot from the planogram + camera.
        locate_goal = LocateSlot.Goal()
        locate_goal.sku = self.sku
        slot = self.call(self.locate, locate_goal, "locate_slot")
        if slot is None:
            return self.safe_stop("could not locate slot")

        # Step 6 — place the product into that slot, upright.
        place_goal = PlaceProduct.Goal()
        place_goal.slot_pose = slot.slot_pose   # reuse locate's output
        if self.call(self.place, place_goal, "place_product") is None:
            return self.safe_stop("place failed")

        # Step 7 — verify it is in the slot and standing.
        verify_goal = VerifyPlacement.Goal()
        verify_goal.slot_pose = slot.slot_pose
        if self.call(self.verify, verify_goal, "verify_placement") is None:
            return self.safe_stop("verification failed")

        self.get_logger().info("unit placed and verified")

    def safe_stop(self, reason):
        # v1 policy: log and stop, never re-plan around a problem.
        self.get_logger().error(f"SAFE-STOP: {reason}")


def main():
    rclpy.init()
    node = Supervisor()
    node.run_once()
    node.destroy_node()
    rclpy.shutdown()
```

Walking through the important blocks:

- **Parameters.** `declare_parameter` registers `sku` and
  `planogram_path` so they can be set at launch without editing code —
  the same demo can stock soup cans or, later, a different SKU, by
  flipping one launch argument. The `planogram` (the small static file
  mapping slot → SKU, slot origin pose, facings, and spacing) is passed
  by path, not hard-coded.
- **One client per action.** Each of the five layers advertises its
  action under the agreed name (`navigate_to_shelf`, etc.). The
  supervisor holds a client for each. The name string is the only
  contract between layers — change it on one side and they stop talking.
- **`call()` — the blocking helper.** Sending an action goal is normally
  asynchronous (section 4), but the supervisor genuinely has nothing to
  do but wait for the current step, so we use
  `spin_until_future_complete` to block until the goal is accepted, then
  again until the result arrives. It returns the result on success or
  `None` on failure, which makes the sequence read top-to-bottom.
- **The sequence in `run_once`.** This is requirements §6 in code: drive,
  pick, locate the slot, place, verify. Notice how `locate_slot`'s result
  (`slot.slot_pose`) is fed straight into `place_product` and
  `verify_placement` — data flows from one layer to the next through the
  supervisor.
- **Failure handling.** Any failed step short-circuits to `safe_stop`,
  which only logs and halts. This is deliberate: v1 never re-plans around
  a problem (requirements §7). Looping `run_once` until the tray is empty
  is the obvious next step, and is where a Behavior Tree replaces this
  hand-written `if` ladder.

### Why the same nodes run in sim and on hardware unchanged

This is the payoff of the whole middleware choice. The supervisor never
mentions Gazebo, Isaac Sim, or any motor. It only sends action goals and
reads results over ROS 2. What changes between simulation and the real
robot is **only the bottom layer**:

- In **simulation**, the action servers and topics
  (`/wrist_camera/color/image_raw`, `/scan`, `/odom`, `/cmd_vel`,
  `/joint_states`) are produced by the simulator's ROS 2 bridge — Gazebo
  publishes the lidar `/scan`, accepts `/cmd_vel`, and so on.
- On **hardware**, those exact same topics and actions are produced by
  real device drivers — a real lidar publishes `/scan`, a real motor
  controller consumes `/cmd_vel`.

Because both sides speak identical ROS 2 interfaces, the supervisor,
the perception node, the planner — every node above the drivers — runs
**byte-for-byte unchanged**. Moving from sim to a real shelf is a swap
of drivers, not a rewrite. That is precisely why this project is
simulation-first and why ROS 2 is the foundation everything else is
built on.
