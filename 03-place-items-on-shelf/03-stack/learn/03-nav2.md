# Learn: Nav2 — the mobile-base navigation layer

> **Nav2** is the part of the robot's software that drives the wheeled
> base from where it is to a precise spot in front of the right shelf,
> and holds it there so the arm can work. This doc teaches Nav2 from
> zero for someone who can program but has never touched a robot. It is
> the hands-on companion to the layer write-up in
> [`../03-mobile-base-navigation.md`](../03-mobile-base-navigation.md).
> Unsure about a term? Check the glossary
> [`../../02-glossary.md`](../../02-glossary.md). This doc assumes you
> already read the ROS 2 intro [`02-ros2.md`](02-ros2.md) — we lean on
> nodes, topics, and actions without re-explaining them.

## 1. Introduction and basic concepts

**Autonomous navigation** is the skill of moving a robot from point A
to point B by itself, without anyone steering it. Think of it as the
robot version of a car's GPS plus the driver: it has to know where it
is, decide on a route, follow that route, and not hit anything on the
way.

For a wheeled robot, navigation breaks into five plain-language jobs.
Keep these five words in mind — every Nav2 concept later slots into one
of them.

- **Map** — have a picture of the building it drives in. For us that
  picture is a top-down floor plan of the grocery aisle showing where
  the walls and shelves are.
- **Localize** — figure out *where on that map the robot currently is*.
  This is the hard part: the robot only sees its surroundings through
  sensors, so it has to match what it sees to the map to place itself.
- **Plan** — draw a route on the map from the current spot to the goal
  spot, going around known obstacles like shelves.
- **Drive** — actually turn the wheels to follow that route, adjusting
  in real time as it goes.
- **Avoid** — if something unexpected appears in the way, react to it
  instead of plowing through.

**Nav2** (short for "ROS 2 Navigation") is a free, open-source software
stack that does all five of those jobs for you. A "stack" here just
means a bundle of cooperating programs, the same way a web stack bundles
a server, a database, and a cache. You do not write the path-planning
math yourself; you configure Nav2's ready-made pieces and send it goals.

Two things to know about how Nav2 is built:

- **It runs on ROS 2.** ROS 2 (Robot Operating System 2) is the
  messaging layer — the way separate robot programs ("nodes") talk to
  each other over named channels ("topics") and request long-running
  jobs from each other ("actions"). If web apps talk over HTTP, robot
  nodes talk over ROS 2. Nav2 is a set of ROS 2 nodes. You already met
  these ideas in [`02-ros2.md`](02-ros2.md).
- **It is driven by a Behavior Tree.** A **Behavior Tree** (BT) is a
  little flowchart that decides what to do next: "try to follow the
  path; if you get stuck, spin in place to clear the sensor; if that
  fails too, back up and retry." It is like a configurable decision
  flowchart for the robot's reactions. Nav2 ships a default tree, and
  you can edit it as an XML file without recompiling anything.

**What we actually need for this project (v1).** Our robot stocks a
grocery shelf. The navigation job is deliberately small: drive reliably
to a **fixed picking pose** — a single, pre-decided standing spot in
front of a target shelf — and stop there steady enough for the arm to
reach. We are *not* asking Nav2 to weave through a busy store. The store
is empty while the robot works. If a person does step into the aisle,
the correct v1 behavior is a **safe-stop**: freeze the base, do not try
to clever-route around them. (A "pose" is a position plus a facing
direction — where the robot stands *and* which way it points.) That
narrow goal — reliable point-to-point driving with a safe-stop — is the
whole bar for this layer.

## 2. Important concepts that are used most often

These are the terms you will hit constantly. Each gets one plain
definition; later sections show them in code.

### The map: an occupancy grid

An **occupancy grid** is the map format Nav2 uses. Picture the floor
overlaid with graph paper. Each little square ("cell") holds one of
three values: free (the robot can stand here), occupied (a wall or
shelf is here), or unknown (never seen). It is literally a 2D image —
black pixels are walls, white pixels are open floor, grey is unknown.
This is why a stored map is just a `.pgm` image file plus a small
`.yaml` file describing its scale and origin.

### SLAM vs localization (slam_toolbox vs AMCL)

These two sound similar but answer different questions.

- **SLAM** stands for "Simultaneous Localization And Mapping." Use it
  when you have *no map yet*. The robot drives around, and SLAM builds
  the map *while* figuring out where it is in the half-built map at the
  same time. Our tool for this is **slam_toolbox**. You run it once to
  create and save the aisle map.
- **Localization** is the easier follow-on job: you *already have* a
  finished, saved map, and you just need to keep answering "where am I
  on it?" as the robot drives. Our tool for this is **AMCL** (Adaptive
  Monte Carlo Localization). The "Monte Carlo" name comes from how it
  works: it scatters hundreds of guesses ("particles") of where the
  robot might be, then keeps the guesses that best match what the lidar
  actually sees. Over a few moves the guesses converge on the true spot.

The normal workflow: use **slam_toolbox** once to build and save the
map, then switch to **AMCL** for every production run on that saved map.
AMCL is lighter and more repeatable when the map is not changing.

### Odometry

**Odometry** is the robot's estimate of how far it has moved based on
its own wheels turning. If each wheel turned this much, the robot must
have rolled forward roughly this far and curved this way. It is fast and
smooth but it *drifts* — small errors add up, like dead reckoning, so it
slowly wanders from the truth. Odometry arrives on the `/odom` topic.
Lidar-based localization (SLAM/AMCL) exists precisely to correct that
drift.

### The tf2 frame chain: map → odom → base_link

Robots track many coordinate systems ("frames") at once and need to know
how they relate. **tf2** is the ROS 2 library that does this bookkeeping
— it continuously publishes the transforms (position + rotation offsets)
between frames so any node can convert a point from one frame to
another. Think of it as a live, always-updating set of "this thing is
*here* relative to that thing" relationships.

The core chain for a mobile base is three frames deep:

```
map  ──>  odom  ──>  base_link
```

- **`map`** — the fixed world frame, locked to the saved floor plan.
  The origin never moves. Goals are given in this frame ("drive to
  x=4.2, y=1.0 on the map").
- **`odom`** — a frame that the odometry drives. It is smooth and never
  jumps, but it slowly drifts away from `map`.
- **`base_link`** — the robot's own body, the frame glued to its chassis.

The localizer (AMCL or slam_toolbox) does *not* move the robot directly.
Its job is to publish the **`map` → `odom`** transform — the correction
that says "your drifty odometry is actually off by this much from the
real map." Wheel odometry publishes **`odom` → `base_link`**. Chain them
and you get the robot's true place on the map. Further down the chain
(`base_link` → ... → `wrist_camera_link`, `tool0`) describe where the
camera and gripper sit on the body — those matter for the arm, not the
base.

### Costmaps (global and local, inflation)

A **costmap** is the map Nav2 actually plans on. It starts from the
occupancy grid but adds a "cost" number to every cell saying how
undesirable it is to be there. Walls get maximum cost; cells near walls
get high cost so the robot keeps a margin.

- **Global costmap** — covers the whole map; used to plan the long route.
- **Local costmap** — a small window that scrolls along with the robot;
  built fresh from live `/scan` lidar data; used for last-second dodging
  and stopping. This is where a person who just walked in shows up.
- **Inflation** — the trick of spreading extra cost outward from every
  obstacle, like a safety halo. With inflation tuned to the robot's
  width, a planned path that avoids high-cost cells automatically keeps
  the whole robot body clear of walls, not just its center point.

### Global planner vs local controller

Two different planners run at two different scales — this trips people
up, so hold the distinction.

- The **global planner** looks at the whole global costmap and computes
  the full route from here to the goal, once, like routing a road trip.
- The **local controller** (Nav2 calls it the "controller") takes the
  next chunk of that route and figures out the exact wheel commands —
  the velocities — to follow it smoothly *right now*, dodging anything
  in the local costmap. It runs many times per second and publishes to
  `/cmd_vel` (the topic the wheels listen to: "drive forward this fast,
  turn this fast").

### Recovery behaviors

When the robot gets stuck — boxed in, lost, path blocked — Nav2 runs a
**recovery behavior**: a canned move meant to un-stick it. The common
ones are *spin* (rotate in place to refresh the sensor view), *back up*
(reverse a little), and *wait* (pause and hope the blockage clears). The
Behavior Tree decides which to try and in what order.

### The Nav2 Behavior Tree and `bt_navigator`

The node that runs the Behavior Tree is **`bt_navigator`**. It is the
conductor: it calls the global planner, hands the route to the
controller, watches for failure, and fires recoveries — all according to
the BT's XML flowchart. When you send Nav2 a goal, you are really
handing a goal to `bt_navigator`, which then orchestrates everyone else.

### The actions: `NavigateToPose` and `FollowWaypoints`

A ROS 2 **action** is a request for a long-running job that reports
progress and can be cancelled — exactly right for "drive over there,"
which takes seconds and might fail partway. Nav2 exposes two we care
about:

- **`NavigateToPose`** — "drive to this one goal pose." This is the
  workhorse for our project: one shelf, one picking pose.
- **`FollowWaypoints`** — "drive through this ordered list of poses, one
  after another." Useful for patrol-style routes or visiting several
  shelves in sequence.

### `nav2_bringup` and the params YAML

You do not start Nav2's dozen nodes by hand. **`nav2_bringup`** is a
package of launch files that boots the whole stack at once. Its behavior
is controlled by one big **params YAML** file — a plain text config (the
same YAML you know from web tooling) that sets every knob: which planner,
how fast the robot may go, how thick the inflation halo is, and so on.
You will spend more time editing this YAML than writing code.

## 3. Hello world example with code

The smallest useful thing: send the robot **one** navigation goal and
print whether it arrived. This is the "drive to a spot" primitive that
everything else builds on.

First, the context — what must already be running. In one terminal you
bring up the simulator and the robot; in another you bring up Nav2 with
its params file and a saved map (AMCL for localization). Bringup is a
launch command, not code:

```bash
# Start the full Nav2 stack: it loads the saved aisle map, starts AMCL
# for localization, the planner, the controller, and bt_navigator.
# map:=... points at the saved occupancy-grid map (the .yaml beside the
# .pgm image). params_file:=... is the big params YAML from section 4.
ros2 launch nav2_bringup bringup_launch.py \
    map:=/maps/aisle_map.yaml \
    params_file:=/config/nav2_params.yaml
```

With that running, here is the Python client. ROS 2's Python library is
called **`rclpy`**. We use its **`ActionClient`** to talk to the
`NavigateToPose` action that `bt_navigator` provides.

```python
#!/usr/bin/env python3
"""Send one NavigateToPose goal and report the outcome."""

import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient

# The message types Nav2 uses. NavigateToPose is the action; PoseStamped
# is a pose (position + orientation) tagged with which frame it lives in.
from nav2_msgs.action import NavigateToPose
from geometry_msgs.msg import PoseStamped


class GoToGoal(Node):
    def __init__(self):
        # Every ROS 2 program is a "node" with a name. This registers us
        # on the ROS 2 network so we can find Nav2.
        super().__init__("go_to_goal")

        # An action client that connects to the "navigate_to_pose" action
        # server living inside bt_navigator. The string must match the
        # action name Nav2 advertises.
        self._client = ActionClient(self, NavigateToPose, "navigate_to_pose")

    def send_goal(self, x, y, yaw_z, yaw_w):
        # Block until Nav2's action server is actually up. Without this
        # we might fire a goal into the void before Nav2 finished booting.
        self.get_logger().info("Waiting for Nav2 action server...")
        self._client.wait_for_server()

        # Build the goal pose. A pose has a position (x, y, z) and an
        # orientation (a quaternion: x, y, z, w). We only drive on a flat
        # floor, so z stays 0 and we only set the z/w parts of the
        # quaternion, which together encode "facing this compass heading."
        goal_pose = PoseStamped()
        goal_pose.header.frame_id = "map"          # coords are on the map
        goal_pose.header.stamp = self.get_clock().now().to_msg()
        goal_pose.pose.position.x = x
        goal_pose.pose.position.y = y
        goal_pose.pose.orientation.z = yaw_z
        goal_pose.pose.orientation.w = yaw_w

        # Wrap the pose in the action's goal message and send it.
        goal_msg = NavigateToPose.Goal()
        goal_msg.pose = goal_pose

        self.get_logger().info(f"Sending goal x={x}, y={y}")
        # send_goal_async returns a future: a placeholder for a result
        # that will arrive later (like a JS Promise). We attach a callback
        # for when Nav2 accepts or rejects the goal.
        send_future = self._client.send_goal_async(goal_msg)
        send_future.add_done_callback(self._on_goal_response)

    def _on_goal_response(self, future):
        goal_handle = future.result()
        if not goal_handle.accepted:
            # Nav2 can reject a goal outright (e.g. it is inside a wall).
            self.get_logger().error("Goal was rejected by Nav2.")
            rclpy.shutdown()
            return

        self.get_logger().info("Goal accepted; driving...")
        # Ask for the eventual result and wait for it the same way.
        result_future = goal_handle.get_result_async()
        result_future.add_done_callback(self._on_result)

    def _on_result(self, future):
        # status == 4 means SUCCEEDED in the ROS 2 action status codes.
        status = future.result().status
        if status == 4:
            self.get_logger().info("Arrived at the goal pose.")
        else:
            self.get_logger().warn(f"Navigation ended with status {status}.")
        rclpy.shutdown()


def main():
    rclpy.init()                     # start talking to ROS 2
    node = GoToGoal()
    # Drive to map coordinate (4.2, 1.0), facing along +x (z=0, w=1).
    node.send_goal(4.2, 1.0, 0.0, 1.0)
    rclpy.spin(node)                 # keep processing callbacks until shutdown


if __name__ == "__main__":
    main()
```

Run it after bringup is up:

```bash
ros2 run my_robot_nav go_to_goal
```

The robot plans a route, drives, and the script prints "Arrived" when it
reaches the spot. That is the entire navigation contract in miniature:
*give a pose in the `map` frame, get back arrived-or-not*.

A note on the quaternion: an **orientation** in 3D is stored as four
numbers called a quaternion. You rarely set them by hand. `(z=0, w=1)`
means "no rotation, facing along the map's +x axis." For other headings
you compute z and w from a yaw angle, which the next section's helper
does.

## 4. A bit advanced example with code

### Following several waypoints

When the robot must visit several spots in order — say, three picking
poses down the aisle — use **`FollowWaypoints`** instead of firing
`NavigateToPose` three times. You hand it the whole ordered list and it
drives them back to back, telling you which ones it missed.

```python
#!/usr/bin/env python3
"""Drive through an ordered list of poses with FollowWaypoints."""

import math
import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient

from nav2_msgs.action import FollowWaypoints
from geometry_msgs.msg import PoseStamped


def make_pose(node, x, y, yaw_radians):
    """Build a map-frame PoseStamped from x, y and a yaw angle.

    yaw is the heading in radians. We convert that single angle into the
    z/w quaternion parts Nav2 expects (valid for flat-floor driving).
    """
    pose = PoseStamped()
    pose.header.frame_id = "map"
    pose.header.stamp = node.get_clock().now().to_msg()
    pose.pose.position.x = x
    pose.pose.position.y = y
    pose.pose.orientation.z = math.sin(yaw_radians / 2.0)
    pose.pose.orientation.w = math.cos(yaw_radians / 2.0)
    return pose


class WaypointRunner(Node):
    def __init__(self):
        super().__init__("waypoint_runner")
        # Note the different action name: "follow_waypoints".
        self._client = ActionClient(self, FollowWaypoints, "follow_waypoints")

    def run(self, poses):
        self._client.wait_for_server()
        goal = FollowWaypoints.Goal()
        goal.poses = poses                      # the ordered list of stops
        self.get_logger().info(f"Following {len(poses)} waypoints.")
        future = self._client.send_goal_async(goal)
        future.add_done_callback(self._accepted)

    def _accepted(self, future):
        handle = future.result()
        if not handle.accepted:
            self.get_logger().error("Waypoint goal rejected.")
            rclpy.shutdown()
            return
        handle.get_result_async().add_done_callback(self._done)

    def _done(self, future):
        result = future.result().result
        # missed_waypoints lists indices Nav2 could not reach. Empty = all
        # visited successfully.
        if result.missed_waypoints:
            self.get_logger().warn(f"Missed: {result.missed_waypoints}")
        else:
            self.get_logger().info("Visited every waypoint.")
        rclpy.shutdown()


def main():
    rclpy.init()
    node = WaypointRunner()
    poses = [
        make_pose(node, 2.0, 1.0, 0.0),     # in front of shelf A
        make_pose(node, 4.2, 1.0, 0.0),     # in front of shelf B
        make_pose(node, 6.5, 1.0, math.pi), # shelf C, facing the other way
    ]
    node.run(poses)
    rclpy.spin(node)


if __name__ == "__main__":
    main()
```

### A slice of the params YAML

The behavior above — how fast, how careful, which planner — comes from
the params YAML, not the code. Here is a trimmed, annotated slice
showing the knobs you will touch first. (Values are illustrative; tune
them for your robot.)

```yaml
# --- The local controller: turns the route into wheel velocities ---
controller_server:
  ros__parameters:
    controller_frequency: 20.0          # recompute wheel commands 20x/sec
    FollowPath:
      plugin: "dwb_core::DWBLocalPlanner"   # the DWB local planner
      max_vel_x: 0.40                     # top forward speed, metres/sec
      max_vel_theta: 1.0                  # top turning speed, radians/sec
      xy_goal_tolerance: 0.10             # "arrived" if within 10 cm
      yaw_goal_tolerance: 0.10            # ...and within ~6 deg of heading

# --- The global planner: draws the full route on the global costmap ---
planner_server:
  ros__parameters:
    GridBased:
      plugin: "nav2_navfn_planner::NavfnPlanner"   # classic NavFn planner
      tolerance: 0.25                     # accept a goal up to 25 cm off
                                          # if the exact cell is blocked

# --- The local costmap: the scrolling window for live obstacle dodging ---
local_costmap:
  local_costmap:
    ros__parameters:
      update_frequency: 5.0
      width: 3                            # a 3 m x 3 m window around robot
      height: 3
      robot_radius: 0.30                  # treat the base as a 30 cm circle
      inflation_layer:
        inflation_radius: 0.55            # safety halo around obstacles (m)
      obstacle_layer:
        observation_sources: scan
        scan:
          topic: /scan                    # the 2D lidar feeds this costmap
          clearing: true
          marking: true
```

The knobs that matter most for our shelf job:

- **`max_vel_x` / `max_vel_theta`** — keep these modest. v1 prizes
  correctness over speed, and a slower base places more repeatably.
- **`xy_goal_tolerance` / `yaw_goal_tolerance`** — how close counts as
  "arrived." Tight tolerances make Nav2 stop more precisely in front of
  the shelf, which helps the arm; too tight and it fusses forever.
- **`robot_radius` + `inflation_radius`** — together these keep the body
  clear of shelves. Set the radius to the real footprint or the robot
  will clip a shelf edge.
- **`scan` / `topic: /scan`** — wires the lidar into the local costmap.
  This is the exact pathway that turns a person walking in into an
  obstacle, which feeds the safe-stop in section 5.

### Swapping slam_toolbox → AMCL on a saved map

During development you run **slam_toolbox** so the robot builds the aisle
map as it drives, then you save that map to disk (a `.pgm` image plus a
`.yaml`). For every run after that, the map is fixed, so you switch the
localization backend to **AMCL**: instead of mapping, AMCL just loads the
saved map and keeps the robot located on it with its particle filter. In
practice this is a launch-time choice — bringup with `slam:=True` to map,
or point bringup at the saved `map:=/maps/aisle_map.yaml` with AMCL for
production. Nothing in your client code changes; the `NavigateToPose`
interface is identical either way. Build once with slam_toolbox, run
forever with AMCL.

## 5. Explanation of place-on-shelf code

Now the real thing. In the project's task loop (see
[`../../01-requirements.md`](../../01-requirements.md) §6), step 2 is
**navigate to the shelf**. The orchestration layer hands us a shelf ID;
our job is to drive to the stored picking pose for that shelf, confirm
arrival, then do a small vision-based nudge to line the robot up squarely
with the shelf face — and only then hand off to the manipulation layer
(`pick_product`).

The picking poses live in a tiny static config file, the same spirit as
the `planogram`. One pose per shelf:

```yaml
# shelf_poses.yaml — the stored picking pose in front of each shelf.
# x, y in the map frame (metres); yaw in radians (which way to face).
shelf_04:
  x: 4.2
  y: 1.0
  yaw: 0.0
shelf_07:
  x: 7.8
  y: 1.0
  yaw: 0.0
```

Here is the `navigate_to_shelf` node. Read it top to bottom; each block
is explained right after.

```python
#!/usr/bin/env python3
"""navigate_to_shelf: drive the base to a named shelf's picking pose,
then nudge into alignment with the shelf face before manipulation."""

import math
import yaml
import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient

from nav2_msgs.action import NavigateToPose
from geometry_msgs.msg import PoseStamped, Twist


class NavigateToShelf(Node):
    def __init__(self, poses_file):
        super().__init__("navigate_to_shelf")

        # Load the stored picking poses once at startup.
        with open(poses_file, "r") as f:
            self._shelf_poses = yaml.safe_load(f)

        # Client for the main Nav2 drive-to-a-pose action.
        self._nav = ActionClient(self, NavigateToPose, "navigate_to_pose")

        # A direct publisher to the wheels, used ONLY for the tiny final
        # alignment nudge. /cmd_vel is the topic the base motors obey.
        self._cmd_vel = self.create_publisher(Twist, "/cmd_vel", 10)

    # ----- the public entry point the orchestrator calls -----
    def go(self, shelf_id):
        if shelf_id not in self._shelf_poses:
            self.get_logger().error(f"Unknown shelf: {shelf_id}")
            return
        self._shelf_id = shelf_id
        entry = self._shelf_poses[shelf_id]      # {x, y, yaw}

        # Build the goal pose in the map frame from the stored config.
        goal_pose = PoseStamped()
        goal_pose.header.frame_id = "map"
        goal_pose.header.stamp = self.get_clock().now().to_msg()
        goal_pose.pose.position.x = entry["x"]
        goal_pose.pose.position.y = entry["y"]
        goal_pose.pose.orientation.z = math.sin(entry["yaw"] / 2.0)
        goal_pose.pose.orientation.w = math.cos(entry["yaw"] / 2.0)

        goal_msg = NavigateToPose.Goal()
        goal_msg.pose = goal_pose

        self.get_logger().info(f"Driving to {shelf_id}...")
        self._nav.wait_for_server()
        future = self._nav.send_goal_async(goal_msg)
        future.add_done_callback(self._on_accepted)

    # ----- Nav2 accepted (or rejected) the goal -----
    def _on_accepted(self, future):
        handle = future.result()
        if not handle.accepted:
            self.get_logger().error("Nav2 rejected the shelf goal.")
            rclpy.shutdown()
            return
        # Wait for the drive to finish.
        handle.get_result_async().add_done_callback(self._on_arrived)

    # ----- Nav2 finished driving: did we actually arrive? -----
    def _on_arrived(self, future):
        status = future.result().status
        if status != 4:                          # 4 == SUCCEEDED
            # Nav2 stopped without reaching the goal. The most common v1
            # cause is the safe-stop: a person stepped into the aisle and
            # the costmap blocked the path. We do NOT push through.
            self.get_logger().warn(
                f"Did not arrive (status {status}); holding for safety.")
            rclpy.shutdown()
            return

        self.get_logger().info("Arrived at picking pose; aligning to face.")
        self._align_to_shelf_face()

    # ----- the short vision-based alignment nudge -----
    def _align_to_shelf_face(self):
        # Nav2 gets us to within ~10 cm of the stored pose, but the arm
        # needs the base squared up to the shelf more precisely than that.
        # We use the wrist RGB-D camera to measure the small remaining
        # angle/offset to the shelf face, then creep the base to zero it.
        angle_error, lateral_error = self._measure_shelf_face_error()

        twist = Twist()                          # a velocity command
        # Proportional nudge: turn to kill the angle, strafe/creep to kill
        # the sideways offset. Gains are small so the move is gentle.
        twist.angular.z = 0.5 * angle_error      # rad/s, cap this in real code
        twist.linear.y = 0.3 * lateral_error     # m/s, holonomic base only

        # Publish the nudge briefly, then stop. (A real version loops until
        # the errors fall under a threshold; kept short here for clarity.)
        self._cmd_vel.publish(twist)
        self.get_logger().info("Alignment nudge sent.")

        # Stop the wheels and declare the base ready for manipulation.
        self._cmd_vel.publish(Twist())           # all-zero = full stop
        self.get_logger().info("Aligned. Handing off to pick_product.")
        # In the full system the orchestrator now triggers pick_product;
        # locate_slot, place_product, and verify_placement follow.
        rclpy.shutdown()

    def _measure_shelf_face_error(self):
        # Placeholder for the perception step (see ../05-perception.md):
        # fit a plane to the /wrist_camera/depth/points cloud, compare its
        # normal and centre to where the shelf face *should* be, and
        # return the small angle and lateral corrections. Returns radians
        # and metres. Here we return zero (already aligned) as a stub.
        return 0.0, 0.0


def main():
    rclpy.init()
    node = NavigateToShelf("/config/shelf_poses.yaml")
    node.go("shelf_04")          # the orchestrator passes the real shelf ID
    rclpy.spin(node)


if __name__ == "__main__":
    main()
```

#### Walking through the blocks

- **Constructor (`__init__`).** Three setup jobs. It loads the
  `shelf_poses.yaml` config into memory once, so a shelf ID can be looked
  up instantly. It opens the `NavigateToPose` action client to talk to
  Nav2. And it opens a publisher to `/cmd_vel` — the wheels' command
  topic — reserved purely for the final alignment nudge. We use Nav2 for
  the long drive and only take direct wheel control for the last few
  centimetres.

- **`go(shelf_id)`.** The entry point the orchestrator calls. It looks
  up the shelf's stored picking pose, refuses cleanly if the ID is
  unknown (never drive to a guess), and packs the config's `x`, `y`,
  `yaw` into a `map`-frame `PoseStamped`. The yaw angle becomes the z/w
  quaternion. Then it waits for Nav2 and sends the goal asynchronously —
  the node stays responsive while the robot drives for several seconds.

- **`_on_accepted`.** Fires when Nav2 says yes or no to the goal. A
  rejection (goal inside a wall, localization not ready) is caught here
  before any driving happens. On acceptance it subscribes to the final
  result.

- **`_on_arrived`.** The key safety block. ROS 2 action status `4` means
  SUCCEEDED. **Any other status means the drive did not complete** — and
  in v1 the most likely reason is the **safe-stop**. We log it and stop;
  we deliberately do not retry or route around, matching the requirement
  that the robot freezes for a person rather than maneuvering near one.
  Only on a clean success do we proceed to alignment.

- **`_align_to_shelf_face`.** Nav2's goal tolerance leaves the base
  within ~10 cm and a few degrees of the stored pose. The arm needs
  better than that, so we close the gap with vision. We measure the small
  remaining angle and sideways offset to the shelf face, then publish a
  gentle `Twist` (a velocity command: linear + angular speeds) to creep
  the base into square. Then we publish an all-zero `Twist` — a full stop
  — and declare the base ready. Control passes to `pick_product`, then
  `locate_slot`, `place_product`, and `verify_placement` further down the
  task loop.

- **`_measure_shelf_face_error`.** The seam to the perception layer
  ([`../05-perception.md`](../05-perception.md)). The real version fits a
  flat plane to the wrist camera's point cloud on
  `/wrist_camera/depth/points`, compares that measured shelf face to
  where the planogram says it should be, and returns the tiny angle and
  lateral corrections. Stubbed to zero here so the navigation flow reads
  cleanly on its own.

#### How a person in the aisle becomes a safe-stop

Trace it end to end through the concepts from section 2. A shopper steps
into the aisle. The base's 2D lidar sees them and publishes the hit on
`/scan`. Nav2's **local costmap** ingests `/scan` (the `obstacle_layer`
in the params YAML) and marks those cells as occupied, with the
**inflation** halo making the blocked zone a little bigger than the
person for safety. The **local controller**, now unable to find a safe
velocity through blocked cells, stops driving — it commands zero on
`/cmd_vel`. The **Behavior Tree** in `bt_navigator` may try a recovery
(a short wait), but with the path still blocked the action ends in a
*non-success* status. That non-success lands in our `_on_arrived`
handler, which logs and holds instead of pushing through. The robot has
safe-stopped — exactly the v1 behavior the requirements call for, with no
crowd-routing cleverness anywhere in the loop.

That is the navigation layer end to end: map and localize with
slam_toolbox/AMCL, plan and drive with Nav2's planner and controller,
keep clear with costmaps and inflation, and treat any blockage as a
safe-stop. Once the base is parked and squared to the shelf, the arm
takes over.
