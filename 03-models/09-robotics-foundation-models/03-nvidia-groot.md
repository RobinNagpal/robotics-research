# 03 — NVIDIA GR00T (N1 / N1.5)

> **The product:** NVIDIA's **open**, **humanoid**-focused robot
> foundation model — download the code and weights, fine-tune it on your
> own robot, and lean on NVIDIA's simulator and synthetic-data tools to
> get there.
>
> Part of [`../`](../README.md). Read
> [`../02-vision-language-action-models/00-introduction.md`](../02-vision-language-action-models/00-introduction.md)

## What it is

**Isaac GR00T N1** (announced ~early 2025) and its update **GR00T
N1.5** are NVIDIA's entry in the robotics-foundation-model race. Like
the others profiled here it is mostly a **Vision-Language-Action (VLA)
model** — it takes camera images plus a plain-language instruction and
outputs robot motion — but it has two defining choices that set it
apart:

- It is **open**: the code lives in a public GitHub repository
  (`Isaac-GR00T`) and the trained weights are published on the model
  hub (Hugging Face), so you can download it, run it, and **fine-tune**
  it on your own hardware.
- It is aimed especially at **humanoids** — two-armed, often two-legged
  robots — though it is **cross-embodiment** ("cross-body": one model
  trained to drive several different robot bodies; see
  [`00-introduction.md`](00-introduction.md)), so it is not *only* for
  humanoids.

"GR00T" is a **stylized product name** — NVIDIA expands it as
*Generalist Robot 00 Technology*, a play on a well-known fictional
character. Treat it as a brand, not a literal abbreviation; the "N"
versions (N1, N1.5) are successive model releases, like software
version numbers.

It also ships with **training tools**, not just a model file: the same
simulation and data-generation stack NVIDIA sells to roboticists (the
**Isaac** family — explained below). That bundling is the whole
personality of the product.

## What makes it distinctive

### A dual-system "think then act" design

GR00T is built as **two cooperating systems**, a split NVIDIA borrows
from a popular idea about fast vs slow thinking:

- **System 2 — the slow "thinking" half.** A **vision-language model**
  (a network that reasons over images and text together) looks at the
  scene and the instruction and works out *what to do* — the plan and
  intent. This is deliberate and comparatively slow.
- **System 1 — the fast "doing" half.** A separate, lighter **action
  module** turns that intent into the actual stream of motor commands,
  running fast enough to drive a real robot smoothly. In the language
  of [`01-working.md`](../02-vision-language-action-models/01-working.md)
  this is an **action head** producing **action chunks** (short bursts
  of upcoming moves).

The plain-language picture: one half *understands the task*, the other
half *moves the body* — and they run at different speeds so the slow
reasoning never stalls the fast control loop. This mirrors the
thinking/doing split you also see in Gemini Robotics' separate
"Embodied Reasoning" model.

### Heavy use of simulation and synthetic data

The other distinctive bet is **where the training data comes from**.
Teaching a robot normally means collecting thousands of real
demonstrations by hand — slow and expensive. NVIDIA's answer is
**synthetic data**: examples *generated by a computer* instead of
recorded from real robots.

- **Isaac Sim / Isaac Lab** — NVIDIA's robot **simulator** (a physics
  game-engine for robots) and its learning toolkit. You can spin up
  thousands of virtual robots, randomise lighting, objects and camera
  angles, and record perfect, labelled trajectories cheaply.
- **GR00T-Dreams / the synthetic-trajectory pipeline** — tools that
  *generate* plausible robot motions and training clips (including from
  generative video models), multiplying a few real demonstrations into
  many synthetic ones.

The pitch is that you can train or fine-tune largely **in simulation**,
then transfer to the real robot — the same simulation-first staging
this repository recommends elsewhere. The catch is **lock-in**: this
workflow is most convenient inside NVIDIA's Isaac ecosystem (and on
NVIDIA graphics processing units, or **GPU**s). A benefit if you live
there already; a commitment if you do not.

### How it compares to its two siblings

- vs **Gemini Robotics** (Google DeepMind,
  [`01-gemini-robotics.md`](01-gemini-robotics.md)): Gemini Robotics is
  the most capable generalist but is **API-only / partner-gated** (an
  **Application Programming Interface (API)** is a set of functions you
  call over the network — you do not get the model file). GR00T is the
  opposite trade: **open weights you host yourself**, in exchange for
  living in NVIDIA's tooling.
- vs **Physical Intelligence π** ("pi",
  [`02-physical-intelligence-pi.md`](02-physical-intelligence-pi.md)):
  both are open and downloadable. π is known for smooth, dexterous
  manipulation on many arms and is ecosystem-light; GR00T leans
  **humanoid** and comes welded to NVIDIA's simulator/synthetic-data
  stack.

## How you get access

GR00T is **open** on both halves that matter:

- **Code** — the `Isaac-GR00T` repository on GitHub (loaders, the
  policy class, fine-tuning scripts, examples).
- **Weights** — the pretrained N1 / N1.5 checkpoints (the trained model
  files) on the Hugging Face model hub.

You will want an NVIDIA **GPU** to run or fine-tune it, and you get the
most value if you also use Isaac Sim / Isaac Lab for data and transfer.

| Model | Body focus | Open weights? | Ecosystem | Bottom line |
|---|---|---|---|---|
| **GR00T N1** | Humanoids, cross-body | **Yes** (GitHub + model hub) | NVIDIA Isaac (Sim/Lab + synthetic data) | First open release: the humanoid foundation model you can host yourself |
| **GR00T N1.5** | Humanoids, cross-body | **Yes** | NVIDIA Isaac | Refined successor — better instruction-following and data efficiency; the one to start from |

*(All versions, dates and claims here drift fast — re-check the repo and
NVIDIA's docs before quoting anything.)*

## A teaching sketch: load GR00T and get an action

> **Teaching sketch, not a guaranteed-runnable script.** This shows the
> *shape* of the API. Exact class and method names follow the current
> `Isaac-GR00T` repository and **will change** — check its README.
> Running or fine-tuning needs an **NVIDIA GPU**; there is no
> CPU-only path that is practical.

**Install.**

```bash
# A recent NVIDIA GPU is expected; the repo ships its own instructions.
git clone https://github.com/NVIDIA/Isaac-GR00T.git
cd Isaac-GR00T
pip install -e .                 # "-e" installs it in editable form
```

**Minimal code to load it and ask for an action.**

```python
# Goal: load a pretrained GR00T policy, hand it one observation (a
# camera image + the robot's joint readings + an instruction), and
# print the action chunk it proposes. This is "inference" — using a
# trained model, not training one. Names follow the Isaac-GR00T repo
# and may change; check current docs.

import numpy as np                       # NumPy: arrays of numbers
from gr00t.model.policy import Gr00tPolicy   # the policy class from the repo

# 1. Download the pretrained GR00T weights from the Hugging Face model
#    hub (first run only; afterwards they are cached on disk). The
#    "embodiment" tag tells the model which robot body — and so which
#    set of joints — these actions are for.
policy = Gr00tPolicy.from_pretrained(
    "nvidia/GR00T-N1.5-3B",              # the published checkpoint name
    embodiment_tag="gr1",                # which robot body to drive
)

# 2. Build one "observation": everything the robot senses right now.
#    Images are grids of red-green-blue (RGB) colour values; "state" is
#    the robot's current joint readings. Here we use blank stand-ins —
#    on a real robot these come from the camera and the joint sensors.
observation = {
    "video": np.zeros((1, 256, 256, 3), dtype=np.uint8),  # one RGB frame
    "state": np.zeros((1, 32), dtype=np.float32),         # joint readings
    "annotation.human.task_description": "place the can on the shelf",
}                                         # the plain-language instruction

# 3. Ask the policy for an action. GR00T returns an *action chunk* —
#    several upcoming moves at once (see 01-working.md) — which the
#    robot plays out before asking the model again.
action = policy.get_action(observation)

# 4. The action is arrays of numbers: target joint angles / hand motion
#    over the next several timesteps, plus gripper open/close. On a real
#    robot you would feed these to the motion controller; here we print.
print("proposed action keys:", list(action.keys()))
print("action chunk shape:", {k: np.shape(v) for k, v in action.items()})
```

**What you should see.** After the (large) download, the keys and
shapes of the predicted action chunk — for example several future
timesteps, each a row of joint commands plus a gripper value. On a real
robot you would execute those rows in order, then ask again.

## Strengths and limitations

**Strengths**

- **Genuinely open** — download the weights, run them, **fine-tune** on
  your own data; no per-call API dependency or network round-trip.
- **Best-in-class for humanoids** and explicitly **cross-body**, so
  skills can transfer between robot designs.
- **Batteries-included data path** — Isaac Sim / Isaac Lab and the
  synthetic-data pipeline let you generate training data cheaply instead
  of hand-collecting thousands of real demonstrations.
- **Dual-system design** keeps slow reasoning from choking the fast
  control loop.

**Limitations**

- **NVIDIA lock-in** — the smooth path assumes NVIDIA GPUs and the
  Isaac ecosystem; you can use the model without them, but you lose much
  of the advantage.
- **Hardware-hungry** — like any multi-billion-parameter VLA it wants a
  capable GPU to run at useful speed (see
  [`../01-basics/03-running-models-hardware-and-tools.md`](../01-basics/03-running-models-hardware-and-tools.md)).
- **Simulation-to-real gap** — synthetic data is cheap but never a
  perfect match for the messy real world; transfer still takes care.
- **Fast-moving and humanoid-tilted** — APIs churn between releases, and
  if your robot is a simple arm, the humanoid framing may be overkill.
- **Still data-dependent** — "foundation model" does not mean "no data";
  good fine-tuning demonstrations (real or synthetic) still matter.

## When to reach for it

- You are building on or simulating a **humanoid** (or several robot
  bodies) and want one model to cover them.
- You are **already in NVIDIA's world** — NVIDIA GPUs, Isaac Sim / Isaac
  Lab — and want the data-generation and sim-to-real tooling to come for
  free.
- You need **open weights you can host and fine-tune** privately, and
  the API-only Gemini Robotics is a non-starter.

Consistent with the rest of this repo, treat a frontier foundation
model as a **later upgrade**, not a starting point: prove your task with
simpler, predictable methods first (geometric perception, scripted or
imitation-learned motion), then reach for GR00T when you genuinely need
its generality — or, in GR00T's case, when you want to learn a policy in
simulation and transfer it (the path in
[`../07-reinforcement-learning-policies/00-introduction.md`](../07-reinforcement-learning-policies/00-introduction.md)).
